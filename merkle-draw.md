# Merkle Draw Protocol

#### Version: 0.2
#### Date published: July 27, 2026

## Purpose

This specification describes a protocol for a random, lottery-style, drawing where chances are represented by SHA256 hashes. The canonical application for this protocol is selecting a particular cryptocurrency transaction from a collection of transactions to reward sender(s) and/or recipient(s) included in the transaction. This reward would, most appropriately, be done in the form of an on-chain "airdrop" of funds

## Background

Bitcoin uses [Merkle trees](https://en.wikipedia.org/wiki/Merkle_tree) as part of the block header to provide an efficient means of validating that a particular transaction is contained within a given block. Comprehensive Bitcoin node and wallet libraries contain Merkle tree functionality. Given a set of "chances," represented by unique, (pseudo)random 256-bit numbers, the same Merkle tree libraries used for Bitcoin can be used to conduct a provably fair random drawing.

## Specification

### Random Drawing Procedure

1. A set of 256-bit numbers, such as those generated by the SHA256 algorithm, are ordered: big endian, ascending (lowest value at `0` index)
2. The Merkle root of the set is calculated, using double-SHA256
3. The Merkle root is added to the original set and the set is ordered again, placing the newly included root at the proper index
4. The winner of the drawing is the "hashing partner" of the Merkle root: the member the first step of the root's Merkle proof/branch would hash it with. Where `i` is the index of the Merkle root in the reordered set, the hashing partner is the member at index `i XOR 1`
5. If index `i XOR 1` falls beyond the end of the set, the Merkle root is the final member of an odd-sized set. Merkle construction duplicates a trailing member, so the proof would pair the root with itself and name no chance at all. In this case, and only this case, the winner is the member at index `i - 1` instead

Step 5 applies to one drawing in every `n + 1`, where `n` is the number of chances, and only when `n` is even. An implementation that omits it produces a drawing with no winner at that rate.

#### Multiple Winner Variation

For a drawing where there are multiple winners, after each winner is drawn, the Merkle root and the winning number are removed from the set and the process is started again to get the next winner. Each round therefore consumes one chance, and the procedure ends once the requested number of winners has been drawn or the set is empty, whichever comes first.

### Code

Reference code for conducting a Merkle Draw using [checkout-components](https://github.com/hansekontor/checkout-components) JavaScript library

```js
const { 
    bcrypto: {
        Hash256,
        merkle 
    }
} = require('@hansekontor/checkout-components')
const { randomBytes } = require('crypto')

// First construct array of all transaction ids to draw from
const leafCount = 500000;
const leaves = [];
for (let i = 0; i < leafCount; i++) {
    leaves.push(randomBytes(32))
}

// Sort array in ascending order (lowest value to highest, big endian)
leaves.sort(Buffer.compare)

// Get the Merkle root
const [root, ] = merkle.createRoot(Hash256, leaves);
console.log('merkle root', root)

// Add the Merkle root into the leaves and sort again
leaves.push(root)
leaves.sort(Buffer.compare)

// Find the index of the root in the leaves array and find it's hashing partner... the winner
const rootIndex = leaves.indexOf(root)
// The hashing partner of index i is index i XOR 1. That index is past the end of
// the array only when the root sorted last in an odd-sized set, which is the case
// Merkle construction would pair with itself. Take the preceding member instead.
const partnerIndex = (rootIndex ^ 1) < leaves.length ? rootIndex ^ 1 : rootIndex - 1
console.log('Winning transaction ID:', leaves[partnerIndex].toString('hex'))

```

## Changelog

### 0.2

Split the winner selection of 0.1 step 4 into steps 4 and 5. Step 4 states the hashing partner directly as index `i XOR 1` rather than by computing a Merkle branch; the two are equivalent, and the index form makes step 5 expressible. Step 5 is new and covers the case where the Merkle root sorts last in an odd-sized set: 0.1 assumed the root's hashing partner was always "an existing member of the set," but Merkle construction duplicates a trailing member, so in that case the proof pairs the root with itself and the drawing names no chance. Under 0.1 this produced a drawing with no winner in one drawing of every `n + 1` for even `n`. Outcomes are otherwise unchanged from 0.1.
